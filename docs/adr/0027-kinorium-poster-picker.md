# ADR-0027: Выбор постеров Kinorium без API-ключа

- **Status:** Superseded by ADR-0028 (подготовка изображений; остальные решения сохранены)
- **Date:** 2026-11-15

## Context

Ручное копирование постеров мешает заполнению домашнего каталога. Пользователь
хочет попробовать интеграцию без запроса ключа Kinorium, без миграций и изменения
схемы существующей БД. Публичные поисковые подсказки сайта возвращают JSON через
`/handlers/Search/?str=…` с заголовком `X-Requested-With: XMLHttpRequest`.
Официальный API `db.kinorium.com` не используется.

Проверка на фильме 776186 подтвердила поиск, метаданные оригинала 2000×3000 и
загрузку исходного JPEG. Прямой запрос галереи получает проверку браузера;
результат Playwright зависит от сессии. Повторная проверка с видимым Chromium
открыла живую галерею и дала 60 постеров. Пользователь согласен проходить капчу
вручную. `iframe` исключён: галерея отдаёт `X-Frame-Options: SAMEORIGIN`, а
same-origin policy не позволяет каталогу читать её DOM.

## Decision

Поиск, парсинг и загрузка находятся в `lib/covers/kinorium-*`, HTTP-обёртки в
`app/api/covers/kinorium`. Запросы выполняются по действию пользователя, с таймаутом
на заголовки **и тело**, ограничением размера ответа и небольшим ограниченным кэшем
в памяти процесса. HTTP-клиент и парсер не используют Prisma и не записывают файлы.

Поиск показывает фильмы с оригинальным названием и годом; совпадения по году
поднимаются выше, но фильм всегда выбирает пользователь. Основной постер доступен
независимо от галереи. Парсер галереи использует `data-photo`, `data-photo-hd`,
`data-preload`, размеры и идентификатор из контракта публичного `photoGallery`
скрипта сайта. Заблокированная или изменившаяся страница возвращает явный статус,
а не притворяется пустой галереей. Парсер проверен на живой галерее; минимальный
HTML fixture сохраняет варианты с HD-ссылкой и без неё, без cookies и метаданных
пользователя.

При недоступной галерее кнопка «Загрузить через браузер» вызывает same-origin POST
`/[id]/browser`. `kinorium-browser.ts` открывает **видимый** Chromium через
Playwright с отдельным постоянным профилем `data/kinorium-browser/` (gitignored).
Профиль сохраняет cookies между визитами. Личный профиль пользователя не читается.
Пользователь проходит капчу сам; код ждёт DOM галереи выбранного фильма, повторно
проверяет URL, передаёт HTML общему парсеру и закрывает окно. Максимум три минуты,
одно окно одновременно; abort, ручное закрытие и ошибки освобождают профиль.
Замок в globalThis переживает dev HMR. Поиск и прямой HTTP-путь работают без
установленного Chromium; установка браузера — отдельная команда, не postinstall.

Для скачивания выбранного изображения используется отдельный same-origin GET.
Он принимает только HTTPS-изображения в `/movie/` на точном наборе CDN-хостов
Kinorium, запрещает редиректы, проверяет MIME и размер до 10 МиБ. Это сохраняет
исходные байты и исключает зависимость от CORS CDN или перекодирования через canvas.
Изображение передаётся существующему `ImageCoverUpload` как `File`.

| Решение интерфейса | Опора | Назначение |
|---|---|---|
| Переключение «Файл или ссылка» / «Kinorium» в текущем окне | `ImageCoverUpload`, design-system проекта | Сохранить единый предпросмотр и подтверждение |
| Строки фильмов с годом, затем сетка постеров 2:3 | `MovieForm`, `MovieCard`, задача пользователя | Различать ремейки, выбирать по изображению и размеру |
| Золотая отметка выбранного постера, штатные Button/Modal | Cinematic Tech, Refero craft-details | Использовать существующие токены и клавиатурные действия |

Обложка меняется только после обычного подтверждения. Создание фильма буферизует
файл до сохранения карточки. Новых полей, таблиц, миграций и фоновых заданий нет.
Браузерный профиль не связан с SQLite. Сохранение использует уже существующий
маршрут обложки и существующее поле `coverPath`.

## Consequences

**Плюсы:** без ключа и регистрации интеграции; основной постер уже проверен на живом
сайте; можно откатить код без отката схемы БД. Проверки запускаются с копией SQLite,
браузерные проверки блокируют записи; рабочая БД не меняется.

**Минусы / trade-offs:** внутренний поиск и HTML не имеют стабильного внешнего
контракта. Сайт может снова запросить капчу или запретить доступ. Браузерный путь
требует установленного Chromium, его системных библиотек и графического сеанса
на компьютере с web-сервером (в WSL — WSLg). При недоступности этого пути доступны
основной постер, ссылка на галерею и прежняя загрузка файлов/ссылок.

Автоматического прохождения капчи, переноса cookies личного браузера и изменений
БД в интеграции нет.
